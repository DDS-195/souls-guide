# 创作者申请整改说明

日期：2026-09-09。

## 业务规则

- 普通、未封禁用户可提交；理由去除首尾空白后必须为 1–500 个 JavaScript 字符单位，前后端一致。
- 每次申请生成独立 ID；同一用户最多一条待审申请。驳回后重新提交创建新记录，不覆盖原理由。
- 提交和审核均先锁定用户行。审核必须绑定申请 ID，同时验证待审状态和用户角色；旧页面、重复或并发审核返回 409，不作用于新申请。
- 封禁账号禁止通过，允许驳回并说明原因。驳回原因必填，1–500 字。
- 申请结果、审核人用户名快照、审核时间、用户角色/状态和结果通知在同一事务提交。
- 记录随申请人账号删除级联删除；审核人删除时保留其用户名快照。通用操作日志不作为申请历史的唯一依据。

## API 契约变更

- `POST /api/users/apply-creator`：`{reason:string}` 必填，成功返回 `{id:number}`。
- `GET /api/users/me`：增加 `application`（最新一轮申请，或 null），包含 id、reason、status、submitted_at、reviewed_at、reject_reason、legacy。
- `GET /api/admin/applications`：分页参数及 `status=pending|processed`，默认 pending。列表 id 是申请 ID，user_id 是用户 ID；包含申请理由、时间、结果、审核人、驳回原因及用户展示信息、user_status。
- `PUT /api/admin/applications/{id}/approve`：路径 id 仍为用户 ID，body 必须为 `{application_id:number}`。
- `PUT /api/admin/applications/{id}/reject`：body 必须为 `{application_id:number,reason:string}`。
- 审核参数错误 400，目标用户不存在 404，申请失效或封禁账号通过请求 409。
- 新 creatorship 通知的 target_id 是申请 ID；正文携带编号，页面入口转到“我的”查看最新状态。旧通知保留原数据，不据其 target_id 查询申请。

## 页面

管理员页仅保留待审核/已处理、分页、刷新和确认弹窗。修复空态与列表并存、重复操作、旧请求覆盖和空页问题。用户入口明确区分待审/驳回，提交后刷新当前用户，驳回理由支持回读。申请弹窗复用 AppModal。

## 数据迁移与发布

新增 `006_creator_applications`，通过 `npm run db:migrate` 或服务启动执行；不删除原有申请字段。旧非管理员用户的最后一轮申请迁入新表，legacy=1；无法还原的申请时间、审核时间和审核人保留 NULL 并显示历史缺失提示，不使用注册/资料更新时间冒充。

用户表 apply_status/apply_reason 是兼容状态镜像，只允许 applicationService 维护。已移除旧的独立写入入口。pending_user_id 是事务维护的唯一占位列，处理完成释放，不使用与当前 MySQL 级联外键不兼容的生成列。

前后端需同步部署；旧客户端不携带申请编号会收到 400，刷新页面后使用新契约。

## 回归测试

新增 11-applications.suite.js：非法理由、并发提交、审核记录回读、重新申请及旧编号冲突、封禁审批、并发审批唯一通知、已处理列表与权限。原申请测试改为真实提交后审核，不再直接写用户状态模拟申请。
