# 系统通知整改

## 规则

- 指定用户（默认）与全部启用用户显式区分，空 ID 不再隐式群发。指定用户必须存在且启用。
- 发送前预览身份/预计人数并确认完整纯文本；内容 trim 后 1～300 个 Unicode 码点。发送后不可编辑、撤回。
- `request_id` 标识一次逻辑发送，同一管理员重试沿用编号。相同编号、不同内容/范围返回 409；同一内容使用新编号属于新的发送。
- 管理员账号行锁串行化其发送请求，先查询幂等结果，再限制一分钟最多 10 个新批次。
- 批次记录、通知 INSERT SELECT、实际写入人数同事务提交。失败全部回滚；零接收人不生成成功批次。
- 批次保留发送人、目标身份快照、完整内容、人数、时间。用户后续删除不删除批次；旧通知不伪造历史记录。批次包含个人信息，应按管理员权限访问并另行制定保留周期。
- 接收人数是实际写入通知中心人数，不等于已读/推送送达人数；预览不预留接收人。
- 未确认请求在当前浏览器标签页 sessionStorage 保留，刷新可安全重试；主动放弃后再发送需新编号，会提示重复风险。

## 接收端

- 已读接口成功后重查列表和未读数，失败不伪造已读。
- 全部已读重置分页；单条已读后补齐列表并纠正空页；加载请求序号防止过期响应覆盖。
- 同秒通知以 id 倒序保证固定顺序。

## 部署和验证

- 先运行 `npm run db:migrate`（新增 008_notification_batches），再重启后端；前后端应一起发布，旧发送接口不再接受隐式范围。
- 新增 13-notifications 测试套件覆盖权限、参数、预览、并发幂等、编号冲突、群发人数、事务回滚、排序、已读隔离和限频；在独立测试数据库运行。
- 当前保持同步数据库写入，不引入队列。大规模用户下需另行压测和评估异步批次。
